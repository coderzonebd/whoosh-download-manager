## How this was measured

- **Machine:** Intel(R) Core(TM) i5-10210U CPU @ 1.60GHz (8 logical CPUs), 7.5 GiB RAM, linux x86_64 7.2.15-76070215-generic, host `pop-os`.
- **Machine load:** load average 4.22/2.77/2.53 at the start and 0.57/0.89/0.92 at the end; the 1-minute load when each run started had median 0.67 (range 0.09–4.00). 2998 MiB of RAM were available at the start. **These numbers are this machine's baseline under that load, not universal truth.**
- **Server:** vayu-labserver started in-process by the harness (content cache 256 MiB). Clients and server share the machine and talk over loopback HTTP/1.1, so a client's CPU use competes with the server's.
- **Runs:** 7 per client × scenario × file unless the scenario says otherwise; within each scenario/file block, all clients' runs are shuffled (seed 20261113) so load drift spreads evenly. Each run starts cold: empty download directory, private HOME/XDG directories, labserver counters reset after the previous client's connections closed. A client that times out twice in a block is skipped for the rest of that block.
- **Metrics:** *time* (the speed metric) = client process start to the download being complete: process exit for curl, wget, aria2c, aria2-next and vayu (`vayu get` returns when the download is done), which exit as soon as the file is done; for MDM and Surge, which download into a partial file, rename it when done and then linger (MDM's CLI reports on a 0.5 s tick; Surge's `--exit-when-done` first checks after 4 s), the moment the download directory holds the full-size file and no partial/control file (polled every 5 ms; the harness then stops the process); for Gopeed, its REST API reporting the task done (polled every 10 ms; time counts from the server's start). *exit* = start to process exit (or to that stop). *durable* = start to the finished file being on disk: once completion is detected (before a lingering client is stopped) the harness fsyncs the output file and its directory and counts until that returns; *sync ms* is that sync's own duration, near zero for a client that already synced (vayu, power-safe by default). labserver's last-byte timestamp (`last_byte_s` in the raw data) is not used for speed: on loopback the kernel buffers megabytes per connection, so the server finishes well before the client, and more so for many-connection clients. *MiB/s* = file size / time; *TTFB* = client start to the first body byte leaving labserver; *peak conns* = most TCP connections the client held open to the scenario at once (idle keep-alive included; max over all runs, failed ones too) and *peak reqs* = most in-flight requests; *CPU* = user + system time of the client process tree; *RSS* = its peak resident set. Speed statistics use successful runs only. A run is **ok** only if the file's SHA-256 matches labserver's digest (of either version, for the changing file).
- **Resident daemon (vayu):** before each run the harness starts the daemon with a fresh data directory and waits until it is ready (not timed; median start-up 10 ms), then measures the CLI as the client. The daemon's CPU during the run (utime + stime from `/proc/<pid>/stat`, 1/CLK_TCK resolution, counted until it goes quiet after the CLI exits, at most 0.5 s) is added to *CPU*, and its peak resident set during the run (`VmHWM` after resetting it through `/proc/<pid>/clear_refs`) to *RSS* (the sum of both peaks). The daemon is stopped after the run, outside the measured window.
- **Idle-machine guard:** before each run the harness sampled how busy the rest of the machine was (200 ms) and read the load average; busy = 1-min load above 4.00 or other processes on more than 1.00 CPUs; it waited for idle (up to 300 s per run; -0 s in total). Other processes used a median of 0.10 CPUs before a run. Every run started on an idle machine.
- **Statistics:** median, p90 (linear interpolation) and min of *time*; *p vs best* is a two-sided Mann-Whitney U test of the client's times against the fastest client's (exact distribution without ties, normal approximation with tie correction otherwise); needs ≥ 3 successful runs on both sides.
- **When:** 2026-11-12T22:23:09Z → 2026-11-12T23:11:08Z (48 min). Harness `vayu-bench 0.1.0` at commit `9665f1bf8f3b`.
- **Command:** `target/release/vayu-bench run --seed 20261113 --bin vayu=~/projects/download-manager/target/release/vayu --bin vayu-cold=~/projects/download-manager/target/release/vayu --label 2026-11-13-pop-os-phase1-gate4 --wait-for-idle --idle-timeout 300 --quiet`
