## How this was measured

- **Machine:** Intel(R) Core(TM) i5-10210U CPU @ 1.60GHz (8 logical CPUs), 7.5 GiB RAM, linux x86_64 7.0.11-76070011-generic, host `pop-os`.
- **Machine load:** load average 1.91/1.79/1.68 at the start and 4.11/3.24/2.74 at the end; the 1-minute load when each run started had median 2.59 (range 0.51–5.74). 3866 MiB of RAM were available at the start. **These numbers are this machine's baseline under that load, not universal truth.**
- **Server:** vayu-labserver started in-process by the harness (content cache 256 MiB). Clients and server share the machine and talk over loopback HTTP/1.1, so a client's CPU use competes with the server's.
- **Runs:** 7 per client × scenario × file unless the scenario says otherwise; within each scenario/file block, all clients' runs are shuffled (seed 20261110) so load drift spreads evenly. Each run starts cold: empty download directory, private HOME/XDG directories, labserver counters reset after the previous client's connections closed. A client that times out twice in a block is skipped for the rest of that block.
- **Metrics:** *time* (the speed metric) = client process start to the download being complete: process exit for curl, wget, aria2c and aria2-next, which exit as soon as the file is done; for MDM and Surge, which download into a partial file, rename it when done and then linger (MDM's CLI reports on a 0.5 s tick; Surge's `--exit-when-done` first checks after 4 s), the moment the download directory holds the full-size file and no partial/control file (polled every 5 ms; the harness then stops the process); for Gopeed, its REST API reporting the task done (polled every 10 ms; time counts from the server's start). *exit* = start to process exit (or to that stop). labserver's last-byte timestamp (`last_byte_s` in the raw data) is not used for speed: on loopback the kernel buffers megabytes per connection, so the server finishes well before the client, and more so for many-connection clients. *MiB/s* = file size / time; *TTFB* = client start to the first body byte leaving labserver; *peak conns* = most TCP connections the client held open to the scenario at once (idle keep-alive included; max over all runs, failed ones too) and *peak reqs* = most in-flight requests; *CPU* = user + system time of the client process tree; *RSS* = its peak resident set. Speed statistics use successful runs only. A run is **ok** only if the file's SHA-256 matches labserver's digest (of either version, for the changing file).
- **Statistics:** median, p90 (linear interpolation) and min of *time*; *p vs best* is a two-sided Mann-Whitney U test of the client's times against the fastest client's (exact distribution without ties, normal approximation with tie correction otherwise); needs ≥ 3 successful runs on both sides.

- **Command:** `target/release/vayu-bench run --seed 20261110 --bin vayu=target/release/vayu --label 2026-11-10-pop-os-phase1-labserver --quiet`
